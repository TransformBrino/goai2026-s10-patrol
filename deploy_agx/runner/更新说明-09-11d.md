# runner 更新说明 · 2026-09-11d（替换 09-11c；上真机必须用这一版）

**一句话**：机器人发 `/IMU_DATA` 用的是 **BEST_EFFORT**，runner 一直用 **RELIABLE** 订阅，两者 QoS 不兼容，**真机上 runner 从来没收到过一帧 IMU**。策略一直是在"角速度恒为 0、重力方向恒为竖直"的输入下跑的，而且没有任何报错（09-11 16:18 AGX 侧查实，昨晚的日志同样全是 0）。0911d 把订阅改成 BEST_EFFORT，并加了一道闸：收不到新鲜的 IMU 就不起立、不进 RL。0911c 的单位修复保留。

## 1.【必须】IMU 订阅 QoS（`interface/robot/hardware/dds_interface.hpp`）
- 改前：`create_subscription<drdds::msg::ImuData>("/IMU_DATA", 10, …)`。只写深度 10 时默认 QoS 是 RELIABLE。
- 改后：`create_subscription<drdds::msg::ImuData>("/IMU_DATA", rclcpp::SensorDataQoS(), …)`，即 BEST_EFFORT、KEEP_LAST 5。BEST_EFFORT 的订阅对 RELIABLE 和 BEST_EFFORT 两种发布者都兼容，真机和仿真通用。
- 依据：
  - AGX 侧：rl_deploy.log 里 118 次打印的 rpy、acc、omg 全是 0；日志报了 `offering incompatible QoS … RELIABILITY_QOS_POLICY`；`ros2 topic info -v` 显示两个发布者都是 BEST_EFFORT。
  - 训练侧核对了 09-10 真机录包的元数据：`/IMU_DATA` 发布者是 best_effort；`/JOINTS_DATA` 和 `/BATTERY_DATA` 是 reliable。所以关节和电池数据一直收得到，这次只动 IMU 这一路。
  - `/height_scan`：AGX 上的 hmap_node.py 用默认 QoS（RELIABLE）发布，runner 的订阅（深度 2，RELIABLE）与之兼容，高程图一直收得到，不改。
- MuJoCo 里一直没暴露的原因：仿真桥发 `/IMU_DATA` 用的也是 RELIABLE，和旧的订阅正好匹配。仿真桥现在加了 `S10_SIM_IMU_QOS` 开关，设成 best_effort 就和真机一致。

## 2. IMU 闸门（新文件 `include/utils/imu_gate.hpp`；改 idle、liedown、standup 三个状态）
- 拦三个入口：空闲→起立、趴下→起立、起立→进 RL。
- 满足以下任一条件就不放行：
  - 从没收到过 IMU；
  - 按本机收到数据的时刻算，IMU 已超过 `S10_IMU_MAX_AGE_MS`（默认 100 ms）没有更新；
  - 读数非法：NaN、|姿态角|>π、|角速度|>π rad/s，或加速度模长不在 0.1g~3g 之间。
- 被拦时每秒打印一次，例如：`!! [IMU] 不起立：从没收到过 /IMU_DATA。（0911d 闸门：收到新鲜 IMU 之前不起立、不进 RL）`
- 已经在 RL 里的时候不强制切换状态，因为断流时强行卸力同样危险。这时只由 safe_controller 每秒打印一次断流告警。
- idle_state 里原有的 `ImuDataNormalCheck`（|omg|>π 等判据）其实从来没被调用过，`GetNextStateName` 只看 `joint_normal_flag_`。现在这些判据都并进了闸门。

## 3. 接收统计与去重（`dds_interface.hpp`）
- 收到第一帧时打印：`[IMU] /IMU_DATA 姿态角按【弧度】读（S10_IMU_RPY_UNIT=rad，默认）；订阅 QoS=BEST_EFFORT（0911d）`
- 2 s 后打印一次接收频率，之后每 60 s 打印一次：`[IMU] 近 2 s 收下 /IMU_DATA N 帧（约 X Hz），丢弃重复/乱序 M 帧；当前 rpy(rad) …（0911d）`。真机上应为约 200 Hz、丢弃约 0 帧（AGX 17:38 实测：单路 200 Hz，报文时钟与接收时钟速率 1.00）。
- 去重规则：
  - 时间戳不大于上一帧的就丢掉。这样两个发布者如果发的是同一帧，只会收一次。
  - 如果已经 0.5 s 没收下任何一帧，下一帧无条件接收，防止机器人时钟跳变后一直被丢。
  - 时间戳为 0 的帧不做去重。
- 新鲜度一律按本机收到数据的时刻算，不用报文里的时间戳。原因见 §5.2。

## 4. `include/utils/safe_controller.hpp`
- 原来的断流判断写的是 `if (current_time_ - imu_check_time_ == 0.2)`，这是浮点数相等比较，基本不会触发。
- 现在改成按本机收到数据的时刻判断断流：超过 100 ms 没收到就每秒打印一次 `imu lag warning`。只打印，不改变控制。
- IMU 的 NaN 检查保持不变。出现 NaN 时 `safe_control_mode` 置 2，起立、RL、趴下三个状态会转到阻尼，3 s 后回到空闲。真实数据不会出现 NaN。

## 5. 订阅修好后第一次被真实数据走到的三处（对应 AGX 侧提的三个风险点）
1. **角速度的单位和坐标系是对的。**
   - 09-10 真机录包里，`/IMU_DATA` 的 omega 和"由姿态角（弧度）微分换算出的机体角速度"之比：x 为 1.06，y 为 0.98，z 为 1.01（相关系数 0.98、0.98、0.997）。
   - 和 `/IMU_103`（标准 sensor_msgs/Imu，单位 rad/s）逐帧比，比值是 1.000。
   - 结论：单位是 rad/s，坐标系是机体系，正负号一致。runner 原样使用这个值，没有做 Deg2Rad；obs[0:3] = omega × 0.25，和训练里的 base_ang_vel 一致。仿真桥发的是 MuJoCo 陀螺仪读数，也是机体系 rad/s，同样一致。
2. **录包里只看到一路 IMU 数据。**
   - 09-10 录包里 `/IMU_DATA` 共 4961 帧，时间戳互不相同，每帧递增 5 ms，没有重复，也没有两路交替。
   - 0911d 仍然按时间戳去重兜底，统计行里会报丢弃了多少帧。
   - **更正（17:45）**：我原先说"机器人报文时间戳只按实际时间的一半在走"是错的。AGX 17:38 实测报文时钟与接收时钟速率 1.00、单路 200 Hz；09-10 那个包是录包端跟不上、按顺序积压（/IMU_DATA 与 /JOINTS_DATA 都只覆盖约 24.8 s 真实时间却录了 51 s）。机器人时钟与 AGX 差约 43 s 仍是事实，所以新鲜度按本机收到的时刻来算仍然必要。dds_interface.hpp 注释里"只按实际一半在走"那句同样不对，只是注释，为保持已装文件的 md5 不改。
3. **safe_controller 和 idle 状态的 IMU 检查：** 见 §2、§4。上墙时俯仰再大，|姿态角| 也不会超过 π。闸门只在起立和进 RL 这两个入口判断，RL 过程中不判断，所以不会在上墙半路误触发。

## 7. AGX 上怎么换
1. 只换上表里的 7 个文件。imu_gate.hpp 是新文件，放到 `include/utils/` 下。然后重编 s10_sdk_deploy。
2. 用 `grep -a` 核对新二进制：`grep -ac 0911d rl_deploy` 应 ≥1，`grep -ac S10_IMU_MAX_AGE_MS rl_deploy` 应 ≥1。
3. 第一次起 runner 时狗趴着。日志里应依次看到：
   - `[IMU] /IMU_DATA 姿态角按【弧度】读（…）；订阅 QoS=BEST_EFFORT（0911d）`
   - 约 2 s 后：`[IMU] 近 2 s 收下 /IMU_DATA 约 400 帧（约 200 Hz），丢弃重复/乱序 0 帧…`
   - 空闲状态每秒打印的 rpy、acc、omg 不再是 0，acc 的模长约为 9.8。

4. 如果看到 `!! [IMU] 不起立：…`，说明闸门在拦，也就是 IMU 没到或者不新鲜。不要去改 `S10_IMU_MAX_AGE_MS` 绕过它，先查话题。

## 8. MuJoCo 验证（09-11 17:00，仿真按真机用 BEST_EFFORT 发 IMU）

## 9. 对 09-10 以来真机结论的影响（部分结论；延迟推断正在重做）
- 收不到 IMU 时切 ClimbH 上 33 cm：翻车，横滚峰值 175°。0911d 之前，真机上任何一次上墙尝试都会是这个结果。
- 收不到 IMU、延迟 0 ms 的平地直行：V1H 的 wz 标准差 0.8°/s，FlatFast_11996 为 0.0°/s。也就是说，在 MuJoCo 里，光是"没有 IMU"并不会产生 09-10 真机上那种偏航自激（1.41 Hz，wz 标准差 31°/s）。
- 之前"真机等效执行延迟约 15~20 ms"的结论，是在仿真里 IMU 正常的条件下标定的，而真机当时根本收不到 IMU，前提不成立，**作废**。
- 按真机当时的条件（收不到 IMU）重扫了延迟（17:05~17:09）：旧的 FlatFast_11996，平地 1.0 m/s，仿真用 BEST_EFFORT 发 IMU。

  09-10 真机实测是 1.41 Hz、wz 标准差 31°/s。收不到 IMU、30 ms 延迟时，摆动频率和真机一样，但幅度只有真机的四分之一；到 40 ms 幅度变大了，频率却不对了。没有哪一档延迟能把频率和幅度同时对上，**所以真机延迟没法再从 09-10 的数据倒推**。只能说：如果那次摆动是延迟造成的，延迟大约在 30 ms 以上；也不排除执行器、摩擦等其它差异。
- **对 0911d 首次上真机的提醒**：有了 IMU 以后，没做过延迟随机化的旧策略（FlatFast_11996、V1G）从 20 ms 起就会剧烈摆头。包里现在的五个策略训练时都随机加过 0~60 ms 延迟，13:54 在有 IMU 的条件下测过 40 ms，平地都稳（V1H 0.8°/s、V1Down 1.1°/s、FlatFast16 0.0°/s、TrotE 0.9°/s）；在 0911d + BEST_EFFORT 条件下的复核结果（平地 1.0 m/s）：V1Down 在 30/45/60 ms 时 wz 标准差为 1.1/1.2/1.4°/s，实际速度 0.83~0.84 m/s；V1H 为 0.7/0.8/1.8°/s，实际速度 0.87~0.88 m/s。两者都稳。
